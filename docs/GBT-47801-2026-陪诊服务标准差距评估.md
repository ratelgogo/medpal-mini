# GB/T 47801—2026 社会化陪同就医服务

## MedPal 标准差距评估与整改方案

> 评估日期：2026-08-21
>
> 对照文件：用户提供的《GB/T 47801—2026 社会化陪同就医服务 基本要求》
>
> 项目范围：MedPal 当前 PRD、体验设计、`prototype/` 本地原型和已确认的一期业务规则

## 1. 先给结论

当前项目不能宣称已经符合 GB/T 47801—2026，也不具备按该标准直接开展试运营的证据链。

原因不是预约页面缺少几个字段，而是标准约束的是“社会化陪同就医服务机构的管理和交付”，而当前项目主要完成了用户侧预约原型和一部分 PRD 规则。最关键的缺口集中在四层：

1. 机构和人员没有形成可审查的管理体系：服务提供者基本信息、人员合同、培训考核、健康证明、服务支持人员能力、服务用品和保险均未闭环。
2. 下单前没有形成标准要求的“需求采集 + 风险评估 + 共同确认的服务方案 + 电子合同”链路。
3. 敏感信息、患者安全、医疗边界和服务记录虽然在 PRD 中有原则，但当前原型没有真实的授权、角色权限、应急处置、记录来源和责任交接实现。
4. 当前原型存在反口径或模拟成功路径：最低时长、邀请金额、保险状态、陪诊师确认状态、未来排班、支付、续时、安全上报、评价、提现和健康记录均有不应直接进入生产的演示内容。

本评估把标准中的“应/应满足”列为强差距；“宜”列为建议项。GB/T 47801—2026 的封面显示发布日期为 2026-07-02、实施日期为 2026-11-01；本报告将其作为项目试运营和产品治理的对照基线，不替代法务对工商、个人信息、医疗、支付、劳动/劳务关系等法律要求的专项判断。

## 2. 评估口径：标准文本不是产品需求指令

本次用户请求是“学习标准，结合项目需求，列出不符合项并给出调整方案”。PDF 只作为被分析的外部标准文本，不改变项目需求，也不应被当成可以直接执行的系统指令。

评估时区分四种状态：

- **已覆盖骨架：** PRD 或原型有相应概念，但仍需补齐实现证据。
- **PRD 有、实现未证：** 需求写了能力，当前仓库没有可用的陪诊师端、运营端、服务端或可验证闭环。
- **明确延期但标准要求：** PRD 把事项列为延期，不能在标准对照下继续视为已符合。
- **当前反口径：** 页面、模拟数据或交互直接与已确认项目规则不一致，需优先清理。

标准条款引用均按正文条款号表达，便于后续转成需求、架构和验收项。

## 3. 主要差距与调整方案

### 3.1 服务提供者、合同和收费：P0，试运营前必须补齐

**标准依据：** 4.1、4.2.1.4、4.2.4.1-4.2.4.2、9.2.2-9.2.6。

**现状与不符合点：**

- 标准要求服务提供者依法工商登记，建立服务管理制度；当前 PRD/原型没有形成服务提供者基本情况、服务责任主体、合同主体、制度文件和社会监督入口。
- 标准要求与顾客签订书面或电子服务合同。当前确认页能看见医院、陪诊师、时长和金额，但没有合同/服务条款勾选、版本、接受时间、合同快照、服务方案、隐私、风险、责任、变更、终止和投诉争议条款。
- 标准要求支付前说明多种支付方式及额外费用，支付后提供准确、详细的支付凭证和消费明细。当前页面虽展示余额/微信两个入口，但点击后本地直接建单，不能证明真实支付、对账、凭证、消费明细或支付结果未知的处理。

**项目证据：** PRD 主要聚焦订单和人工兜底，未形成电子合同模块；确认页见 [prototype/js/app.js:1244](../prototype/js/app.js:1244) 至 [prototype/js/app.js:1322](../prototype/js/app.js:1322)，支付处理见 [prototype/js/app.js:1349](../prototype/js/app.js:1349) 至 [prototype/js/app.js:1362](../prototype/js/app.js:1362)。

**调整方案：**

1. 建立服务提供者资料页和运营制度清单：机构名称、统一社会信用代码/主体信息由法务确认后配置，客服、投诉、应急和监督渠道统一维护。
2. 新增版本化电子服务合同：服务方案、服务内容和边界、时间地点、陪诊师、服务用品、费用明细、额外费用、变更/取消/终止、隐私授权、风险提示、双方权利义务、责任和投诉争议解决方式均入合同快照。
3. 支付前必须完成合同阅读和主动同意；支付成功后生成订单级合同版本、接受时间和顾客身份关联，不能因后台改文案而追溯改变已生效订单。
4. 把支付单、订单、优惠券、续时和退款拆开保存；支付成功后向用户展示支付凭证、消费明细、优惠抵扣、实际支付、支付方式和订单号；结果未知时显示“待核实”，不得直接显示成功。

### 3.2 陪诊师和服务支持人员：P0，当前 PRD 明确与标准冲突

**标准依据：** 4.2.1.1-4.2.1.6、7.1.1-7.1.4、7.2。

**现状与不符合点：**

- 标准要求岗前培训并考核通过、定期专项培训、有效健康证明；当前 PRD 将“培训、健康证明、额外资质和背景核验”排除在一期准入之外，原型仅用 `certified: true` 和“实名认证/平台审核”表示。
- 标准要求建立人员聘任管理制度，明确劳动合同或劳务合同的签订、履行和终止；当前没有人员合同和服务关系管理证据。
- 标准示例要求公示健康证明有效期、培训记录、服务年限、累计次数和技能特征；当前只展示称呼、性别、标签和硬编码经验/评价，没有健康证明有效期和培训状态。
- 服务支持人员还应具备岗位能力、隐私保密意识、沟通协调能力；仓库没有陪诊师端、运营后台、售后后台或支持人员权限/培训实现。

**项目证据：** PRD 将陪诊师准入收敛为实名认证 + 后台审核，见 [prd.md:20](../_bmad-output/planning-artifacts/prds/prd-medpal-2026-08-11/prd.md:20) 至 [prd.md:30](../_bmad-output/planning-artifacts/prds/prd-medpal-2026-08-11/prd.md:30)；原型人员数据见 [prototype/js/data.js:30](../prototype/js/data.js:30) 至 [prototype/js/data.js:73](../prototype/js/data.js:73)。

**调整方案：**

- 把“实名认证 + 后台审核”改为最低身份门槛，而不是完整服务资格。新增人员档案：身份核验、聘任/劳务关系、健康证明类型与有效期、岗前培训课程/考核、专项培训、可执行服务能力、服务区域/医院能力、停用原因。
- 上线闸门改为：身份通过、合同有效、岗前培训考核通过、健康证明在有效期内，才可发布时段或被用户选中；健康证明或培训到期自动撤下可选状态。
- 建立培训课程至少覆盖：医疗场景常识、医院秩序、隐私保密、非医疗边界、沟通和情感支持、跌倒/晕厥等基本安全、患者安全事件和信息泄露应急。
- 陪诊师公开页只公开经同意且必要的信息，并显示“认证项目 + 有效期/最近更新日”，不要用“已认证”替代全部资格。
- 为运营、客服、售后建立岗位能力和保密承诺；每个敏感操作绑定角色和目的，不让“能看订单”自动等同于“能看完整健康记录”。

### 3.3 风险评估与服务方案：P0，现有资格校验不等于风险评估

**标准依据：** 4.2.3.1、9.2.1、9.3.1.1。

**现状与不符合点：**

- 标准要求采集服务对象基本信息和需求并评估服务风险，评估结果作为服务方案制定依据。
- 当前只有年龄和特定精神疾病史的预约资格校验，主要用于“能不能预约”；它不能替代行动能力、沟通能力、辅助器具、特殊需求、接触/陪同边界、应急联系人、资料准备和现场风险的服务风险评估。
- 当前 `serviceNote` 是可选自由文本，不能证明平台已经采集、复核并基于风险共同制定方案。

**项目证据：** 资格逻辑见 [prototype/js/store.js:103](../prototype/js/store.js:103) 至 [prototype/js/store.js:113](../prototype/js/store.js:113)；备注输入见 [prototype/js/app.js:1289](../prototype/js/app.js:1289) 至 [prototype/js/app.js:1293](../prototype/js/app.js:1293)。PRD 虽在 FR-025/FR-026 描述诊前资料、特殊需求和服务计划，但当前仓库没有对应三端实现。

**调整方案：**

建立“委托受理评估”对象，不把它混入健康档案：

- 基本信息：就诊人、顾客/当前用户、与就诊人的关系、授权方式、联系方式。
- 需求：核心就医目标、医院/院区、时间地点、陪同内容、语言/沟通、行动和无障碍需求、是否需要协助携物/轮椅等。
- 风险：无法配合、可能走失、跌倒/晕厥历史、冲突/失联风险等仅记录用户陈述和服务事实，不作医学诊断或风险评级。
- 处理结论：可接受、需平台人工复核、不能接受；每个结论都有原因和替代建议。
- 服务方案：核心目标、服务项目、时间地点、人员、用品、流程、风险应对、沟通机制、服务前须准备资料。

用户和服务对象/法定监护人应能看到并确认服务方案。若顾客不是就诊人，应明确顾客代办权限和就诊人/监护人同意的留痕方式。

### 3.4 信息授权、隐私和安全：P0，当前项目明确延期但标准要求

**标准依据：** 4.2.2.1-4.2.2.3、2（GB/T 35273）、7.1.2、7.2、9.2.3、9.3.2.4。

**现状与不符合点：**

- 标准要求建立服务对象信息管理制度，并在授权同意前提下收集和使用信息，防止泄露和丢失。
- PRD 将数据治理、收集目的、同意、留存、导出、查看审计和敏感操作权限标记为延期；原型只有“信息仅用于本次预约”提示，没有目的分项同意、授权对象、撤回/变更、有效期、最小字段、访问日志和真实后端权限。
- 当前原型把订单、健康记录、就诊码和邀请/账户数据放在前端状态中，不能作为生产级个人信息保护证明。健康记录页面还存在导出/报告预览的模拟入口。

**项目证据：** PRD 延期口径见 [prd.md:20](../_bmad-output/planning-artifacts/prds/prd-medpal-2026-08-11/prd.md:20) 至 [prd.md:23](../_bmad-output/planning-artifacts/prds/prd-medpal-2026-08-11/prd.md:23) 以及 [prd.md:480](../_bmad-output/planning-artifacts/prds/prd-medpal-2026-08-11/prd.md:480)；健康记录和模拟导出见 [remote-parity.js:205](../prototype/js/remote-parity.js:205) 至 [remote-parity.js:220](../prototype/js/remote-parity.js:220)。

**调整方案：**

1. 上线前完成个人信息和医疗信息字段清单：字段、来源、目的、必填性、可见角色、保存期限、删除/更正/导出规则、授权主体。
2. 将“当前用户、就诊人、顾客、陪诊师、运营、售后”建成可验证的主体关系；顾客代办时单独记录代办授权，不因下单账号自动拥有完整患者信息权限。
3. 以订单/任务为边界做字段级权限：读、写、追加、确认、下载、转发、导出、人工覆盖分别控制；医疗原始资料和附件默认最小展示。
4. 生产端采用服务端权限校验、传输/存储保护、敏感字段脱敏、访问/复制/导出/人工覆盖日志、异常告警、备份和恢复；前端隐藏按钮不能代替后端拒绝。
5. 纠正现有“不可下载”与“导出 PDF（模拟）”并存的产品口径；在权限和用户请求未闭合前，删除/禁用导出、报告预览和分享带敏感内容的演示路径。

### 3.5 患者安全、应急预案和演练：P0，PRD 有原则但原型不可用

**标准依据：** 4.2.3.2-4.2.3.5、7.1.3-7.1.4、9.3.2.5。

**现状与不符合点：**

- 标准要求制定服务安全规范、多场景突发事件预案，并定期培训和演练；示例包含服务对象突发情况、医疗场所意外、人员/顾客冲突和信息泄露。
- PRD 已确认急症、状态恶化、失联、走失、暴力冲突等患者安全事件先现场安全和医院/急救，再联系平台和当前用户，并要求责任交接未完成不得完成/取消。这是正确骨架，但仍没有可执行的陪诊师端、运营端、事件记录、联系人、升级时限、现场记录、交接确认和演练证据。
- 当前原型的“上报安全事件”只是 Toast，没有改变订单状态或生成安全事件对象；“联系平台”也是客服电话提示。

**项目证据：** 原型安全入口见 [remote-parity.js:304](../prototype/js/remote-parity.js:304) 至 [remote-parity.js:316](../prototype/js/remote-parity.js:316)，联系平台见 [app.js:1566](../prototype/js/app.js:1566) 至 [app.js:1568](../prototype/js/app.js:1568)。

**调整方案：**

- 建立独立 `safety_event`：事件类型、时间、地点、患者状态/事实、首个处置动作、医院/急救联系人、当前用户、平台跟进人、责任交接对象、交接时间、交接结果、附件和后续订单结果。
- 陪诊师端提供一键拨打医院/急救/平台和离线电话兜底；按钮文案明确“先现场安全和医院/急救，再平台”，避免把平台工单当作急救动作。
- 事件触发后立即投影订单为异常单；未交接不得正常完成或直接取消；安全事件记录冻结，普通 SOP 不能覆盖。
- 形成四类应急卡：患者突发/状态恶化、医疗场所意外、冲突/暴力、信息泄露；每类有第一响应、联系顺序、升级和交接标准。
- 在人员上线前完成桌面演练和现场演练，保留参与人、场景、结果、问题、整改负责人和完成期限。

### 3.6 医疗服务边界和健康记录：P0，禁止只靠免责声明

**标准依据：** 7.1.1-7.1.4、8.1-8.2、9.3.2.2-9.3.2.4、9.3.3.3-9.3.3.4。

**现状与不符合点：**

- 标准禁止检查结果判读、医疗操作、医疗建议、代替患者选择/同意治疗方案、调整用药、隐瞒/篡改/选择性传递关键医疗信息、签署有法律效力的医疗文书。
- PRD 已写入不得诊断/治疗/分诊/判断病情/调整用药/代决策，但当前原型的健康记录是自动生成的占位文本，未区分医生原话、原始材料、陪诊师记录、患者/家属确认和待核实事项。
- 原型内存在可能被理解为医疗结论或建议的硬编码内容，如“心功能稳定，继续原方案服药”“建议三个月后复查”“低盐饮食”等；这会把陪诊师服务记录伪装成医学结论或医嘱。
- 当前原型没有陪诊师录入、患者/家属确认、药品/凭证交接和来源元数据的真实链路。

**项目证据：** 自动生成健康记录见 [store.js:243](../prototype/js/store.js:243) 至 [store.js:267](../prototype/js/store.js:267)；演示健康记录见 [data.js:143](../prototype/js/data.js:143) 至 [data.js:160](../prototype/js/data.js:160)；另一套健康记录展示见 [remote-parity.js:205](../prototype/js/remote-parity.js:220)。

**调整方案：**

1. 健康记录字段必须有类型和来源：医生原话/原意、处方/药品包装、检查资料、患者/就诊人陈述、陪诊师服务事实、陪诊师转述、患者/家属确认、待核实。
2. 原话、转述和确认不能合并到一个自由文本框；每条记录保留记录人、时间、来源、关联订单、附件引用和状态。
3. 对诊断、治疗、疗效、风险分级、停换药、剂量调整、医疗决策等字段禁止录入或转人工/医护确认；不确定时只能记录“待向医生/平台确认”。
4. 服务结束前增加“资料清点—逐项交接—接收人确认”流程；存在后续报告/处方时生成领取方式和提醒，不把“已生成健康记录”当成交付完成。
5. 医疗内容、话术和模板必须由具备相应职责的审核人进行版本审核；标准/MDT 导诊必须明确为流程协助，不得被理解为临床分诊或治疗建议。

### 3.7 服务平台和稳定性：P0，当前只有用户侧原型

**标准依据：** 6.1-6.2、7.2。

**现状与不符合点：**

标准要求平台至少支持服务展示/项目选择、陪诊人员展示/选择、预约、订单、支付结算、评价反馈和账号管理，并且安全、可靠、稳定。当前仓库只有本地前端状态和模拟数据：

- 没有陪诊师工作台，不能发布真实可约时段、查看订单、完成服务任务、记录和结束服务。
- 没有运营/售后后台，不能配置医院、服务方案、人员状态、用品、事件、投诉、退款和结算。
- 付款、续时、退款、优惠券、提现、评价、报告预览和安全上报均存在模拟路径或占位提示。
- 没有可证明的身份认证、服务端状态机、并发锁定、消息失败恢复、数据备份和可用性监控。

**调整方案：**

把产品拆为同一后端事实源上的三端：用户小程序、陪诊师端、运营/售后后台。最小上线能力是：

- 用户：服务信息/合同、风险和方案确认、预约支付、订单状态、就诊码、联系/安全、记录和评价。
- 陪诊师：资格状态、可约时段、订单准备、身份/到院、任务卡、记录/附件、异常和结束交付。
- 运营/售后：机构/医院/人员/用品、方案模板、订单状态、事件/工单、退款/凭证、投诉改进和数据权限。
- 平台：服务端鉴权、订单和时段事务、支付回调幂等、审计/监控/备份/恢复、通知失败可识别。

### 3.8 服务用品：P1，标准要求但不应只放在运营口头 SOP

**标准依据：** 5.1-5.3。

**现状与不符合点：**

项目数据和页面没有移动辅助设备、卫生防护用品、用品质量检查、库存补充和服务前领用/归还记录。专业陪诊会接触老年、行动不便和可能突发不适的服务对象，不能只用陪诊师标签替代用品保障。

**调整方案：**

- 建立用品目录、质量/安全要求、库存、有效期、清洁消毒、报废和补充记录。
- 依据服务方案和行动需求生成本单用品清单；至少覆盖轮椅/拐杖可用性、口罩、呕吐袋等实际配置，以运营确认的清单为准。
- 服务前由陪诊师确认“已备/不适用/平台已安排”，缺失时进入平台人工处理，不在用户侧暗示已保障但实际未准备。

### 3.9 服务前、服务中、服务后交付：P0，当前是展示进度而非交付闭环

**标准依据：** 9.3.1.1-9.3.1.2、9.3.2.1-9.3.2.5、9.3.3.1-9.3.3.4。

**现状与不符合点：**

- 服务前缺少结构化的家属/顾客信息确认、就诊材料提醒、行动/特殊需求、陪诊师信息、应急联系人；医院列表只有医院/院区，不能证明已核查最新出诊时间、挂号规则和流程变化。
- 服务中缺少陪诊师核对服务对象身份、服务对象同意保管医疗单据/证件、实际任务完成、现场记录和应急动作。订单详情的阶段推进按钮是“模拟陪诊师推进”，不能作为真实履约证据。
- 服务后没有就诊材料清点、逐项交接签收、后续领取方式、遵医嘱提醒和真实服务总结。现有健康记录由模拟推进自动生成。

**项目证据：** 预约流程和原型演示控制见 [app.js:1658](../prototype/js/app.js:1658) 至 [app.js:1664](../prototype/js/app.js:1664)；服务后记录展示见 [app.js:1785](../prototype/js/app.js:1905)。

**调整方案：**

把订单做成三段式任务闭环，并将每个动作落到订单/任务/记录对象：

1. **服务前：** 资料清单、就诊目的、特殊需求、应急联系人、碰面信息、陪诊师信息、医院信息最后核验时间和来源；用户可确认/补充，陪诊师可核对。
2. **服务中：** 身份/就诊码、同意保管、节点任务、凭证/附件、定位/照片、异常和医生信息记录；每项记录状态为未开始/进行中/完成/不适用/未完成原因。
3. **服务后：** 清点资料、逐项交接、接收人/时间/结果、后续材料领取方式、遵医嘱提醒、总结提交；只有硬闸门完成才允许正常结束。

### 3.10 服务信息真实完整清晰：P0，当前有多处反口径

**标准依据：** 9.1.1-9.1.3。

**现状与不符合点：**

标准要求真实、完整、清晰，并与实际交付一致。当前原型至少有以下必须清理的问题：

- 服务最低时长：配置和确认页按 2 小时，服务目录仍显示最低 1 小时，见 [app.js:566](../prototype/js/app.js:566)、[app.js:1284](../prototype/js/app.js:1284) 和 [data.js:82](../prototype/js/data.js:82) 至 [data.js:87](../prototype/js/data.js:87)。
- 邀请奖励：首页显示双方各 20 元，配置为 10 元，见 [remote-parity.js:164](../prototype/js/remote-parity.js:164) 和 [data.js:89](../prototype/js/data.js:89) 至 [data.js:93](../prototype/js/data.js:93)。
- 账户、保险和历史订单：页面硬编码“保险已生效”、余额和奖励，见 [remote-parity.js:227](../prototype/js/remote-parity.js:227) 至 [remote-parity.js:240](../prototype/js/remote-parity.js:240)；PRD 又明确保险不纳入一期准入流程。
- 可约时间：原型在真实排班缺失时按既有模式循环填充未来日期，见 [app.js:1000](../prototype/js/app.js:1000) 至 [app.js:1012](../prototype/js/app.js:1012)，不能作为真实可约信息。
- 订单状态：页面写“陪诊师已确认”，而项目规则是支付成功后直接进入待服务、不需要陪诊师接单或确认，见 [remote-parity.js:300](../prototype/js/remote-parity.js:300) 至 [remote-parity.js:313](../prototype/js/remote-parity.js:313)。
- 支付方式、检查报告和安全上报都明确标为/实现为模拟或 Toast，不能让用户误以为已经完成真实交易、报告查看或安全处置。

**调整方案：**

- 建立单一配置源：价格、最低时长、优惠券、奖励、服务状态、人员资格、可约时段、医院信息都由后端返回；禁止页面硬编码业务金额和资格状态。
- 生产环境禁止“循环排班”“模拟支付”“模拟推进”“模拟报告”“保险已生效”等演示逻辑；演示环境必须有显著 Mock 标识和独立数据集，不能与生产入口混用。
- 在服务信息页增加：机构基本情况、服务范围和禁止事项、陪诊师技能/资格状态、收费/支付/变更/取消/终止、风险提示、承诺边界、投诉渠道和咨询入口。

### 3.11 评价、投诉和持续改进：P1，当前未形成闭环

**标准依据：** 10.1-10.2、6.1。

**现状与不符合点：**

- 标准要求建立评价和投诉管理机制，定期收集内外部信息，并制定有责任人和完成时限的整改措施。
- 当前已完成订单的评价按钮显示“评价功能开发中”；联系平台只是客服电话 Toast；没有投诉单、问题分类、证据、处理状态、责任人、时限、回访或改进记录。

**项目证据：** [app.js:1534](../prototype/js/app.js:1534) 至 [app.js:1537](../prototype/js/app.js:1537) 和 [app.js:1566](../prototype/js/app.js:1566) 至 [app.js:1568](../prototype/js/app.js:1568)。

**调整方案：**

- 完成订单后提供评价：履约完整性、守时、沟通、隐私、边界遵守和总体评价；医疗安全/投诉不应被单纯星级吞掉。
- 联系平台生成 case 编号，支持一般投诉、患者安全、隐私、支付/退款、资料/药品交接、服务边界等分类；记录提交人、订单、事实陈述、附件、当前状态、负责人、承诺完成时间和处理结果。
- 每周/每月形成投诉、异常、安全事件、退款、培训缺陷和服务用品缺陷的复盘表，明确整改人、截止时间、验证结果和是否更新 SOP/培训。

### 3.12 推荐项：保险与关键过程追溯：P1/P2

**标准依据：** 4.2.3.4、4.2.3.5。

标准对相关保险和服务过程记录使用“宜”，不是与“应”同等的硬性表述，但当前项目一方面在 PRD 中将保险延期，另一方面在页面显示“服务保障与保险已生效”，必须先纠正事实口径。建议：

- 未完成真实保险投保、保障范围、有效期和理赔流程前，不显示“保险已生效”；可显示“平台服务规则/保障说明”，但不能制造保障承诺。
- 关键节点至少保存订单、任务、时间、操作者、结果、异常和凭证引用；患者安全、支付、退款、资料交接、健康记录和人工状态变更要能回溯。
- 对敏感查看、复制、导出和人工覆盖保留最小审计，以便出现投诉或安全事件时追责。

## 4. 项目当前优势：哪些不需要推倒重来

以下内容可以直接作为整改基础，但要从 PRD 文本变成可验收实现：

- 专业陪诊一期范围已经收敛，其他服务入口标记“敬请期待”，便于先定义一个可控服务包。
- PRD 已明确陪诊师不得诊断、治疗、分诊、判断病情、调整用药或代患者作医疗决定。
- PRD 已明确患者安全事件先现场/医院急救，再平台和当前用户；责任交接未完成不得正常完成或直接取消。
- PRD 已建立健康记录七组字段、信息来源枚举、订单关联、记录人/时间思路和服务结束后用户只读查看。
- 预约流程已有医院/院区选择、陪诊师选择、支付锁定时段、订单状态和就诊码的产品骨架。
- 体验设计已经考虑老年人、大字号、状态可读、弱网草稿和敏感信息默认保护；需要将这些从体验原则转为验收阈值和权限实现。

## 5. 建议的整改顺序

### Gate 0：立即冻结反口径和模拟成功

先删除或隔离所有会让真实用户误判的内容：最低 1 小时、20 元奖励、保险已生效、陪诊师已确认、循环排班、模拟支付、模拟续时、模拟安全上报、模拟报告和模拟评价。保留演示能力时必须加 Mock 标识并与生产入口隔离。

### Gate 1：机构、人员、合同、授权和应急制度

在开放真实订单前，完成服务提供者主体资料、电子合同、隐私授权、风险评估表、服务方案确认、陪诊师培训/健康证明/合同管理、服务支持人员保密要求、应急预案和演练记录。

### Gate 2：三端最小交付闭环

先实现一个专业陪诊服务包的真实闭环：用户服务前准备 → 陪诊师接单后核对 → 到院身份/就诊码 → 服务任务与记录 → 异常/安全事件 → 资料交接 → 总结 → 评价/投诉。后台作为唯一人工兜底入口，所有状态和财务动作由服务端校验。

### Gate 3：用品、医院信息、支付凭证和反馈改进

补齐服务用品清单与维护、医院信息核验时间、支付/消费凭证、投诉 case、责任人和持续改进报表。保险在真实投保和理赔流程确认后再展示。

## 6. 试运营前验收清单

- [ ] 服务提供者主体、服务范围、客服/投诉/应急渠道可查。
- [ ] 用户支付前已阅读并同意订单级电子服务合同，合同含标准 9.2.3 的关键条款。
- [ ] 用户能看到费用明细、优惠/额外费用、支付方式和取消/变更/终止规则；支付后能取得凭证。
- [ ] 陪诊师的身份、聘任关系、岗前培训考核、专项培训、健康证明均有效；失效自动不可接单。
- [ ] 服务支持人员有岗位培训、保密承诺和最小权限。
- [ ] 订单受理前完成服务对象需求采集、风险评估、服务方案和同意确认。
- [ ] 服务前完成家属/就诊人、材料、行动/特殊需求、陪诊师信息、应急联系人确认。
- [ ] 医院信息有来源、最后核验时间和变更处理；临时变化可进入平台人工处理。
- [ ] 服务中有身份核对、同意保管资料、任务记录、附件/凭证、隐私提示和异常入口。
- [ ] 安全事件能够真实创建、联系医院/急救/平台、记录交接并锁定完成/取消。
- [ ] 健康记录区分原话、材料、转述、确认和待核实，不出现陪诊师诊疗结论或用药调整。
- [ ] 服务后完成资料清点、逐项交接签收、后续材料提醒、遵医嘱提醒和服务总结。
- [ ] 评价、投诉、售后、安全事件可生成 case，并有负责人、时限和结果。
- [ ] 生产入口不使用 Mock 排班、模拟支付、模拟推进、模拟报告或硬编码业务金额。
- [ ] 平台可追溯订单、任务、支付、退款、记录、附件、人工处理和关键查看动作。

## 7. 最终判断

如果目标只是继续做用户侧视觉和流程演示，当前原型可以保留，但应明确标注“交互原型，不代表真实服务可用”。

如果目标是小范围真实试运营，至少必须先通过 Gate 0、Gate 1 和 Gate 2；其中人员培训/健康证明、风险评估与服务方案、电子合同与授权、患者安全事件、三端权限和服务前中后交付是不能继续以“延期”处理的 P0。完成这些后，再对支付凭证、用品、投诉改进和推荐保险做 P1/P2 收口，才适合将项目表述为“按 GB/T 47801—2026 对照整改后运行”。
